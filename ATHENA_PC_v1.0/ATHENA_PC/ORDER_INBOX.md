# 주문 대기함 v1

상단 **주문 대기함 → 주문 등록**에서 거래처, 접수일, 품목별 수량·단가, 메모를 입력합니다.
거래처와 품목은 기존 등록 목록에서 선택합니다. 한 주문에 1~100종을 입력할 수 있으며,
동일 품목은 한 줄에 합칩니다. 재고 부족과 관계없이 접수할 수 있습니다.

목록에서 주문번호·거래처·품목·메모를 검색하거나 상태로 필터링할 수 있습니다.
25건씩 표시하며 상세, 수정, 상태 변경, 삭제 기능을 제공합니다.

| 상태 | 의미 |
|---|---|
| 대기 | 신규 주문 접수, 내용 확인 전 |
| 확인 | 주문 내용을 확인함 |
| 완료 | 주문 관리가 끝남 |
| 취소 | 주문 접수를 취소함 |

모든 상태는 수동으로 변경하고 잘못 선택하면 되돌릴 수 있습니다. 신규 주문은 항상 대기입니다.
**완료를 포함한 모든 주문 작업은 재고·매출·입금·미수금·반품을 변경하지 않습니다.**
실제 판매가 발생하면 기존 판매·입금 화면에서 별도로 등록합니다. 이번 버전에는 판매 전환,
문자 수집, 카카오톡, AI, RPA, 외부 서비스 연동을 포함하지 않습니다.

삭제는 기존 휴지통 방식으로 처리하여 복구할 수 있습니다. 주문의 원래 거래처·품목명·규격·단위는
스냅샷으로 보존합니다. 기존 거래처나 품목을 보관/삭제해도 기존 주문의 내용을 확인하고 수정할 수
있습니다. 새 주문 및 새로 추가할 참조는 사용 중인 거래처·품목만 허용합니다.

## 구조와 기존 기능 보호

- 기존 구조: `catalog.py`는 품목·거래처·수동 재고, `ledger.py`는 판매·입금·반품,
  `reports.py`는 이들 장부를 합산하여 재고·미수금·매출을 계산합니다.
- 별도 `orders` / `order_lines` 테이블과 `orders.py`를 추가합니다. 기존 장부 테이블과 계산 로직을
  수정하지 않습니다. 주문에는 재고 이동이나 판매·입금 참조를 만들지 않습니다.
- 기존 `Application.write`의 트랜잭션, 요청 키 중복 처리, revision 충돌 검사, CSRF 및 세션 검사를
  그대로 사용합니다. 주문 수정·상태 변경은 `edit_history`에 전후 스냅샷을 기록합니다.
- 목록/상세: `GET /api/orders?q=...&status=...`, `GET /api/order/{id}`.
- 등록/수정: `POST /api/orders` (`id`가 있으면 수정). `partner_id`, `day`, `note`,
  `lines: [{product_id, qty, price}]`를 받습니다. 수정은 상태를 유지합니다.
- 상태: `POST /api/order-status` (`id`, `status`). API 값은 `pending`, `confirmed`, `completed`, `cancelled`.
- 삭제: `POST /api/delete` (`entity: "order"`, `id`), 복구/영구 삭제는 기존 휴지통 API.
- 모든 POST는 기존과 같이 `request_key`와 `revision`이 필요합니다.
- 수량 1~1,000,000, 단가 0~1,000,000,000원, 합계 최대 1,000,000,000,000원.
  접수일은 2000년부터 오늘까지입니다. 미래 배송일 관리는 이번 범위에 포함하지 않습니다.

## DB 업데이트와 백업 호환성

스키마는 v4입니다. v1/v2/v3 장부는 첫 실행 시 기존 데이터 폴더의
`backups/before-schema-v4-날짜-시각.db`에 SQLite 온라인 백업을 먼저 저장한 후 업그레이드합니다.
마이그레이션 DDL과 버전 변경은 한 트랜잭션으로 실행합니다. 백업 실패 시 업데이트하지 않고,
마이그레이션 실패 시 롤백하며 파일 연결을 닫습니다. 알 수 없는 버전은 거절합니다.

현재 백업에는 주문과 주문 수정 이력이 포함됩니다. 이전 v1/v2/v3 백업 복원은 임시 복사본을 v4로
업그레이드한 뒤 기존과 동일한 스키마·데이터 검증을 수행합니다. 주문 품목 수와 합계도 검증합니다.
이전 백업을 복원하면 백업 시점 이후 자료와 주문은 사라지며, 복원 직전 장부는 별도로 보존됩니다.

v4 장부를 이전 프로그램에서 여는 다운그레이드는 지원하지 않습니다. 이전 코드로 돌아갈 때에는
업데이트 전 백업을 별도로 사용해야 하며, 그 백업에는 업데이트 후의 주문/장부 변경이 없습니다.

## 검증 (2026-09-18, Windows / Python 3.12)

프로젝트 폴더에서 실행:

```text
python -B -m unittest discover -s tests -v
python -B tests/check_http_flow.py
node --check ui/orders.js
node --check ui/app.js
node --check ui/forms.js
```

- 기존 회귀 21개 + 주문 테스트 11개: 총 32개 통과.
- 주문 CRUD/상태/휴지통 전 과정에서 기존 8개 장부 테이블과 요약 수치가 변하지 않음을 검증.
- 잘못된 입력·중복 품목·합계 초과의 롤백, 중복 저장, stale revision, 과거 참조 보존 검증.
- v1/v2/v3 업그레이드, 원본 스키마/데이터 백업 보존, 반복 초기화, 백업/DDL 실패 시 보호 검증.
- 주문 포함 백업 복원·재시작, 구버전 백업 복원, 잘못된 주문 합계가 있는 백업 거절 검증.
- 실제 실행기 HTTP 검사: 주문 및 기존 판매→입금→반품, 휴지통, CSV, 백업, 중복 실행, 재시작.
- 분리된 체험 DB의 브라우저 확인: 등록, 재고 초과 접수, 다중 품목 수정, 상세, 완료 상태 필터,
  삭제와 복구. 입력한 HTML 문자열은 실행되지 않고 텍스트로 표시됨.

실제 사용자 장부에는 접근하지 않았으며, 외부 자동화나 실서비스 배포는 수행하지 않습니다.
